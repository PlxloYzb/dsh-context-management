## 当前结论

本轮只改一处检索装填：**命中片段自证所属记录**。此前片段固定回溯 32 个码位，常落在行中；对 `checksum=` 这类泛化值查询，返回的是 `"state=retrying; previous=delta; checksum=f47f1591b3…"`，模型看不出这条命中属于哪条 observation，被迫整块解压 2048 token 才能定位——这正是候选 8 C 臂首次 850 秒轮次超时的现场。现在片段会以所在行的开头文本作前缀，例如 `"Observation 1.0: service=beacon;…state=retrying; previous=delta; checksum=f47f1591b3…"`，被查字面量与局部上下文仍在同一个 100 码位片段预算内。

离线留档回放：175 个命中页、465 条命中中有 264 条属于“行中”命中（旧的 32 码位回溯够不到行首），修复后 **264/264 全部带出记录开头**。装填没有变化：158 个公共调用的命中数逐一相同（336 → 336），总响应字节仅 +173，没有任何调用命中数下降；匹配优先占用片段预算，长查询只会压缩前缀与后文而不会截掉被查字面量。

前缀只展开有界的一段：无换行的文本块其“行首”就是块首，按块大小取前缀会在每次命中分配与整块同量级的数组。改为只取有界前缀后，400k 字符单行块的检索中位耗时从 1.43 ms 降到 0.15 ms，且 221 个无游标留档调用、498 条命中的模型可见响应逐字节相同——因此上述模型门对最终构件依然成立。

冻结构件上的三臂全量探针回归 A/B/C 分别 115/509/356 秒全部通过且归档字节审计通过；同候选另有 C 臂首次 386 秒、事实 23/24（未检索 F19 并给出任何页面都不存在的值）的样本，原样保留。prepack、打包审计、包名安装/卸载和安装后外部类型检查全部通过。尚未发布 npm。

## 为什么片段必须自证记录

候选 8 C 臂首次超时的现场：模型想回答“PAGE-1 第一条 observation 行的 checksum”，却改用了泛化查询 `checksum=`（limit 20），连翻三页游标拿到 15 条命中，再整块解压 2048 token。三次响应里每条命中的片段都形如：

```
"state=retrying; previous=delta; checksum=f47f1591b3. This is diagnostic context, not a change to aut"
```

记录名 `Observation 1.0:` 落在回溯窗口之外，模型无法从片段判断哪条命中属于“第一条 observation 行”，因此必须解压。通过的样本改用 `Observation 1.0` 直接命中，说明问题不在检索本身，而在命中片段缺少记录身份。

修复只在片段构造处增加前缀：当所在行起点早于原来的 32 码位回溯点时，取出该行开头最多 32 个码位接在片段前，行首与局部上下文之间用 `…` 分隔；两者共享原有 100 码位上限，因此单条命中的字节量级不变。预算是按优先级分配的：先保证被查字面量完整可见，再分配前缀与局部上下文，所以长查询只会缩短前缀和后文。同一现场修复后的片段为：

```
"Observation 1.0: service=beacon;…state=retrying; previous=delta; checksum=f47f1591b3. This is diagno"
```

## 判别性、装填与分配回归

新增 R10d：构造两行长记录（第二行含 Unicode 与代理对），断言每条命中都以自己的记录开头（`Observation 1.0:`、`Observation 2.0:`）、仍包含被查字面量与其值、片段不超过 100 码位；再用一条 70 码位的长查询断言**完整字面量**仍出现在片段里，即前缀与后文让位于匹配。新增 R10e 覆盖无换行文本块：块首即“行首”，断言前缀以块首开头而不是按整块分配。两条都在修复前的读取器上失败、修复后通过。本轮 187 单元 + 79 集成通过。

离线装填对照以候选 8 为基线，仅比较两次回放都存在的 158 个调用：命中数完全相同，没有任何调用减少命中，总字节增加 173（约每条调用 1 字节），说明前缀几乎完全由原有片段预算吸收。有界前缀等价性以已提交的候选 9（`99f372c`）为对照，逐调用比较模型可见载荷：221 个无游标调用、498 条命中，0 处不同（游标本身是读取器随机串，不参与比较），因此三臂模型门对修复后的构件依然有效。同机配对基准显示单行 400k 块上检索中位耗时 1.43 ms → 0.15 ms，片段内容相同。
