# 双 Muse minimal：小步云端验证

[English](ITERATION-MUSE-CLOUD.en.md) · [脱敏数据](data/turnover-muse-cloud-2026-09-15.json) · [测试索引](TESTING.zh-CN.md)

承接[上一阶段](ITERATION-MUSE-ENGINE.zh-CN.md)。本轮前台和后台摘要统一为同一真实路由 `opencode-go-muse/muse-spark-1.3-contributor`，思考强度 `minimal`，固定宿主 DSH `0.1.2-rc.1`。每次只启动一个短样本，审查完成结果后决定下一项；不预排批量串行队列。

## 预先确定的协议

1. 增加 `backgroundSummary.allowSameProvider: true` 显式并发配置。默认仍为 false，避免把本地串行服务自动当作并行服务；不用 provider 别名绕过判断。原快照、取消、预算和安全事务约束继续适用。
2. 先做一个 18 页、64k 窗口、25% 准备线的 C 机制样本。确认两类实际请求均为 Muse minimal，记录前台与摘要的流区间、内容区间、并发峰值、是否赶上边界、来源哈希和归档恢复。流重叠不等于底层 GPU 并行。
3. 若请求和事务可审计，再跑同种子 A（关闭后台摘要）对照；随后按证据选择第二种子、默认准备线或故障短样本。自然迟到保留为回退结果，不通过等待摘要来制造成功。种子和检索后分别严格计分，新原文保留单独检查。
4. 引擎改动仍执行真实 Web 三臂门：匹配原生 Basic、插件原地压缩、插件窗口。先用 F3 / 24 页 / 32k 压力 / 6 页一批；窗口臂可打开双 Muse，并做真实重启。按次审查，必要时增加同配置关闭后台摘要的窗口对照，避免把摘要收益与压缩策略混为一谈。
5. token 和请求耗时继续记账；本轮云端门使用 `--cost-control=observe`，不以 token 费用额度终止。每轮/每请求/整项墙钟终止仍保留，以便失败可回收。使用合成会话、实验 profiles、私有 settings；禁用自动标题调用，不改变日常默认项。

关键判据是能否在短前台工作期间完成摘要，以及未完成时能否立即安全回退。答案正确、原文保留、严格工具门和总成本分别报告，不能因一个指标通过就推断其余通过。

## 结论与产品改动

同一云路由的前台与摘要请求可以在宿主中重叠执行；准备充足的机制样本使用了模型摘要，换窗仍约 10 ms。但真实短分页任务在 60% 和 40% 两条准备线下均为 **0/4 次采用**：前三次摘要迟到，末次超出字节额度。把模型换成云端、调低准备线，都不足以保证统筹成功。本轮不修改默认准备线，也不把摘要等待加入换窗路径。

产品仅新增 `backgroundSummary.allowSameProvider`，默认 false；显式 true 允许同 provider 的后台工作。后台功能仍需显式配置。使用者须自行确认路由支持并发；此开关不探测服务端容量。本轮实验配置为：

```yaml
backgroundSummary:
  provider: opencode-go-muse
  model: muse-spark-1.3-contributor
  reasoningEffort: minimal
  allowSameProvider: true
```

准备快照、来源哈希、取消、超时、字节预算、当前输入保护与安全事务沿用上一阶段实现。摘要就绪才在边界消费；未就绪立即用确定性索引回退。配置不会使前台 AgentLoop 并行发出多轮请求。

## 机制样本：准备充足时可用

18 页历史、64k 逻辑窗口、25% 准备线，种子上限 4096 **UTF-8 字节**（配置沿用 `seedMaxTokens` 名称）。同种子 91531，先执行 C，再审查并执行 A。探针含 7 个历史字段；先禁检索，再开放检索。

| 样本后缀 | 后台摘要 | 种子直答 | 检索后 | 前台 / 检索阶段秒 | 换窗 ms | 检索成功 / 尝试 |
| --- | --- | --- | --- | --- | ---: | ---: |
| `cloud-c-91531` | 就绪并采用 | 6/7 | 7/7 | 15.64 / 21.16 | 9.80 | 4 / 4 |
| `cloud-a-91531` | 关闭 | 2/7 | 7/7 | 9.14 / 100.46 | 11.04 | 5 / 5 |

C 的首个摘要请求 10.99 秒，与首个前台流生命周期重叠 10.99 秒；全流程请求峰值 2，其中后台最多 1。内容首块到末块的区间也有约 1.52 秒交集。该结果证明宿主没有把摘要串行等待放进前台路径，不能证明服务端 GPU 的调度方式。

C 实际提交 `model-assisted` 种子 1577 字节，来源哈希吻合，快照之后的前台 assistant 原文仍在活动窗口。A 提交抽取种子 1432 字节，前台原文归档。两者当前用户输入、工具配对、追加式事务、归档分页逐字节恢复均通过。两者最终答案都包含新标记；标记可以来自用户索引，因此“答出标记”和“保留 assistant 原文”分别审计。

A 的检索尾部出现一个 **88.43 秒 / 198 输出 token** 的慢流，不能据此宣称 C 有一般性的端到端加速。这里只报告一组配对观察，未作显著性推断。C 还在下一代次发出第二次摘要，成本统计包含未消费的准备工作。

## 短前台诊断：指令失败不能算摘要收益

将前台任务改为“禁用工具，只回复新标记”，用于缩短摘要可用时间。其余夹具保持不变，逐项审查后才选择下一项。

| 样本 | 前台秒 | 严格单标记指令 | 种子 / 检索后 | 检索成功 / 尝试 | 结果解释 |
| --- | ---: | --- | --- | ---: | --- |
| `cloud-brief-c-91531` | 11.90 | 失败 | 7/7 · 7/7 | 8 / 8 | 原始运行仍标记失败；后续独立审计确认原文保留 |
| `cloud-brief-a-91531` | 6.10 | 通过 | 2/7 · 7/7 | 6 / 6 | 确定性对照 |
| `cloud-brief-c-repeat-91531` | 18.17 | 失败 | 7/7 · 7/7 | 12 / 12 | 重复观察，保留失败 |
| `cloud-brief-c-nocache-91531` | 15.00 | 失败 | 7/7 · 7/7 | 8 / 10 | 私有设置禁 SDK 缓存关联，未解决问题 |

失败 C 样本的前台转而回顾历史，部分还尝试被禁止的 `arc_status`。这种输出延长前台时长、复述历史事实，所以其种子 7/7 **不能当作干净的短工作实验或仅由摘要带来的收益**。`completed` 只表示执行结束；前台指令、种子分数和归档安全分别记录。

第一次失败还暴露测试判据错误：旧执行器靠查找“含新标记的 assistant 消息”确定待保护原文。模型未生成标记时，该定位为空，误报边界连续性失败。现改为定位最新真实用户输入之后的最后一条 assistant 消息，再独立检查标记是否生成。原始失败报告和输出未被改写；离线审计明确保留 `originalRunCompleted: false`，确认实际新原文没有丢失。

### HTTP 归属核验

随后仅运行一个前台诊断 `cloud-wire-c-91531`，没有继续种子与检索探针。测试专用 observer 捕获实际 Muse Responses HTTP 请求及 SSE 响应，原始内容仅存在忽略目录、0600 权限文件，未存储认证头。

- 3 次 HTTP 请求均为 Muse minimal、HTTP 200，响应 ID 独立；一条摘要和两条前台请求分别配对。
- 前台 HTTP 输入确实包含当前单标记指令；首次前台响应本身选择了 `arc_status`，被实验守卫拒绝，下一次前台响应给出历史回顾。
- 宿主最终展示文本与对应前台 HTTP 响应逐字一致；没有观察到本地把摘要响应串给前台。
- 两类请求共享默认 SDK 缓存关联键，但禁用关联的独立样本仍失败。缓存根因假设未获支持，默认缓存设置未改变。

这将问题定位到已经正确送达请求的服务端响应行为，尚不能区分模型指令遵循、云端服务实现或并发影响。单个 wire 诊断不证明因果，也不提供远端计算并行证据。该原始 wire 日志的时间字段是发起时间；并发观察仅依据宿主流生命周期。observer 后续新增独立完成时间，未改写旧日志。额外证据不足前，不修改只读宿主或 SDK。

全部任务执行完成、交付物通过；全部 24 页被真实模型请求完整曝光，归档逐字节审计通过。三个窗口样本均通过真实进程重启后的恢复。原地和 40% 窗口臂全部质量门通过；原生逐字不足，60% 窗口与关闭后台的窗口臂严格工具门失败，因此不能宣称三臂全绿。

两次严格工具失败都是最初 6 个 `experiment_read_page({})` 被拒，之后正确传入页码完成读取；原始失败保留。关闭后台仍出现同类失败，说明这些工具错误并非双路摘要特有。没有模型自愿调用 `compress` 或 `new_context`；自动策略执行了压缩。

原生 Basic 的 4 次压缩在 pre-step 阻塞 **10.59–16.30 秒**；插件原地为 **19–28 ms**，三组窗口为 **20–29 ms**（含宿主 pre-step 的观测区间）。两组开启后台的峰值均为 2 条宿主流，累计前后台交集分别 **18.04 / 19.42 秒**，但全部摘要终止于 late/oversize，没有完成且被采用的摘要。

报告 token 为宿主/适配器提供的使用量，含报告的缓存类别；两组后台各有 3 条被取消的流报告零 usage、1 条超预算流没有 usage，不能推断这些调用免费，也不能将表中 token 当作完整账单。其余请求与未消费的后台工作都在原始日志留存。样本数少、工具错误和云端慢流会改变总耗时；表中时长不能证明某个策略普遍更快。关闭后台的窗口同样达到 3/3 逐字，因此本组没有显示后台摘要的额外答案收益。

### 为何 40% 没有解决默认 60% 的问题

准备线控制 token 压力，不能保证墙钟提前量。两组前三次快照到换窗都只跨约 42–47 个事件，摘要在 pending 状态到达安全换窗边界，被取消后记为 late；流结束不等于摘要 ready。末次为输出超预算，主动终止。两组余量都从约 1.4 KiB 缩到约 0.5 KiB，调低阈值并未改变这一点。

实际可用摘要字节取决于同一 4096 字节种子中用户历史索引、精确记录索引、头部和保留空间的分配。更早冻结还会留下更长、必须原样保留的新后缀；即使摘要完成，替换旧快照也须确实把压力降到许可线。不能把一个已完成摘要无条件当作可用摘要。本组实际没有走到来源收益判定，不能把该潜在限制说成已观察失败。

两点调参均没有采用收益，因此停止阈值扫描。后续应验证“足够安全提前时间 + 足够摘要字节”的调度条件，再决定是否调整快照时机或种子分配；不能靠边界等待把采用率做高。
